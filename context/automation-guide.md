# Automation Guide

This is the rulebook the `automation-engineer` agent follows when turning passed manual test cases
into Playwright scripts. It was generated by the `framework-analyzer` agent from a live snapshot of
the QA app plus the framework's own defaults (there is no pre-existing automation repo to inherit
conventions from — see `context/project-overview.md`).

## Framework & language

- **Playwright Test** (`@playwright/test` 1.64.0) + **TypeScript**.
- Config: `playwright.config.ts` at the repo root (`TB_Agents-main/`).
  - `testDir`: `./data/outputs/4-automation`
  - `outputDir`: `./data/outputs/4-automation/.results`
  - `baseURL`: `process.env.APP_URL` (`https://qa.toolberry.app` in `.env`)
  - `testIdAttribute: 'data-testid'` — configured, but **see "Locator strategy" below: the app does
    not appear to expose `data-testid` in practice**, so this setting is currently mostly inert.
  - `trace: 'retain-on-failure'`, `screenshot: 'only-on-failure'`, single `chromium` project.
  - `fullyParallel: true`, `retries: 0` locally (`forbidOnly` only under `CI`).

## Where files go

```
data/outputs/4-automation/
├── *.spec.ts            # test files, one per module/flow
├── pages/                # page objects
│   └── <Module>Page.ts
└── fixtures/              # shared fixtures (auth, test data setup)
    └── auth.fixture.ts
```

- **Tests:** `data/outputs/4-automation/<module>.spec.ts` (e.g. `transfer.spec.ts`, `jobs.spec.ts`).
  One file per feature module, matching `context/modules/*.md` naming where one exists.
- **Page objects:** `data/outputs/4-automation/pages/<Module>Page.ts`, PascalCase class name
  `<Module>Page` (e.g. `TransferPage`, `JobsPage`).
- **Fixtures:** `data/outputs/4-automation/fixtures/<name>.fixture.ts`. Extend Playwright's `test`
  via `base.extend<...>()`; export the extended `test` and `expect` from a single
  `fixtures/index.ts` so spec files import one thing.
- Test case IDs from `context/test-standards.md` (`TC-<MODULE>-<NNN>`) go in the test title, e.g.
  `test('TC-TRANSFER-001 — create a transfer and ship it', async ({ page }) => { ... })`.

## Page object pattern

One class per module/screen, constructed with the Playwright `Page`, exposing **locators as
getters** and **actions as methods**. No assertions inside page objects — assertions live in the
spec file.

```ts
// data/outputs/4-automation/pages/TransferPage.ts
import type { Page } from '@playwright/test';

export class TransferPage {
  constructor(private readonly page: Page) {}

  // Locators — role + accessible name first (see "Locator strategy")
  get directionField() {
    return this.page.getByRole('radiogroup', { name: 'Direction' });
  }
  get assetsField() {
    return this.page.getByRole('combobox', { name: 'Assets' });
  }
  get saveAndOpenButton() {
    return this.page.getByRole('button', { name: 'Save & Open' });
  }
  get shipLink() {
    return this.page.getByRole('link', { name: 'Ship' });
  }
  shipDialog(transferName: string) {
    return this.page.getByRole('dialog', { name: `Ship: ${transferName}` });
  }

  // Actions
  async open(workspacePath: string) {
    // Prefer UI navigation over goto() — see "Known risks" (deep-link session drop)
    await this.page.getByRole('link', { name: workspacePath }).click();
  }

  async save() {
    await this.saveAndOpenButton.click();
  }
}
```

## Auth: how tests sign in per role

Per `context/roles.md`, **ToolBerry sign-in has no password** — each role is `email + one-time code
emailed at sign-in time`. Env vars follow `process.env.ROLE_<NAME>_EMAIL` /
`process.env.ROLE_<NAME>_PASSWORD` for naming consistency with the framework's convention, but the
`_PASSWORD` var is always empty and unused.

- `ROLE_OWNER_ADMIN_EMAIL` / `ROLE_OWNER_ADMIN_PASSWORD` (unused)
- `ROLE_STAFF_EMAIL` / `ROLE_STAFF_PASSWORD` (unused)
- `ROLE_TEST_EMAIL` / `ROLE_TEST_PASSWORD` (unused)

**Open risk — no fully automated sign-in path exists today.** The one-time code is emailed and a
human types it into the code screen; there is no documented API/backend shortcut (e.g. a seeded
session token, a test-only magic-link bypass, or an email-inbox API Playwright could poll) that
this analysis could verify. Until one of those exists, automated tests cannot sign in unattended
end-to-end.

**Decision: Playwright `storageState` reuse.** A human (the `/qa` session operator) signs in once
per role through the real flow, Playwright saves `storageState` (cookies + localStorage) to a JSON
file under `data/outputs/4-automation/.auth/<role>.json` (gitignored), and the test suite's auth
fixture loads that saved state instead of re-running the login UI per test. This avoids needing a
human in the loop *per test run* but still needs one *per state refresh* (session/token expiry,
unknown TTL — needs confirmation below). When a test run finds the saved state is stale/expired
(e.g. redirected to the sign-in page instead of landing authenticated), it should fail with a clear
message telling the operator to re-capture `storageState`, not retry silently.

```ts
// data/outputs/4-automation/fixtures/auth.fixture.ts (skeleton)
import { test as base } from '@playwright/test';

export const test = base.extend({
  storageState: 'data/outputs/4-automation/.auth/owner-admin.json',
});
```

- **Needs confirmation:** the storage/session mechanism ToolBerry's frontend uses (cookie vs
  localStorage vs IndexedDB/OPFS, given it's described as offline-first) determines whether
  Playwright's `storageState` capture even captures everything needed to resume a session, or
  whether app-local SQLite/OPFS data (noted as "isolated per port" in the main repo's CLAUDE.md)
  also needs seeding. First automated spec written against this guide should verify a captured
  `storageState` actually resumes a signed-in session before relying on it further.
- A test-only backend endpoint or email-inbox API (e.g. Mailpit) was considered and rejected for
  now — not confirmed to exist against the QA environment (`qa.toolberry.app`), only against local
  dev stacks per the main repo's CLAUDE.md. Revisit if CI automation (not just on-demand local runs)
  becomes a goal.

## Locator strategy (priority order)

Based on a live `browser_snapshot` of the authenticated app (Transfer record page) and the
just-completed manual Transfer test run, **the app does not expose `data-testid` (or any other
test-id attribute) anywhere observed** in the accessibility tree — confirmed, not just reported.
Elements are reliably locatable by **ARIA role + accessible name** throughout: e.g.
`navigation "Stages"`, `link "Ship"`, `button "Add"`, `button "More options"`, `combobox "Search"`,
`list` / `listitem` nav items (`button "New Job"`, `button "New Transfer"`, etc.), `main`, `table`.

Priority order for locating elements in new tests:

1. `page.getByRole(role, { name })` — **primary strategy**. The app's accessible names are
   consistently descriptive (verified: buttons, links, comboboxes, radiogroups, dialogs all carry
   meaningful names).
2. `page.getByLabel(text)` — for form fields where a visible/ARIA label exists but the role alone
   is ambiguous (e.g. multiple textboxes in the same form).
3. `page.getByText(text)` — for static content / assertions on visible copy, not for interactive
   elements that have a role.
4. `page.getByTestId(...)` — **kept available in config** (`testIdAttribute: 'data-testid'`) in
    case specific components do carry it (not seen on the pages analyzed so far — Transfer only).
    Re-check per-module before assuming it's absent everywhere; don't rely on it by default.
5. CSS/XPath chains — **last resort only**, and only with a comment explaining why no role/label/
   text locator worked.

Never chain brittle structural selectors (`.q-item:nth-child(3) button`) when a role+name locator
is available — Quasar's internal DOM structure is not a stable contract.

## Waiting

- Rely on Playwright's **web-first assertions** (`expect(locator).toBeVisible()`,
  `toHaveText()`, etc.) and **auto-waiting** built into actions (`click`, `fill`).
- **Never use `page.waitForTimeout()`.** If a wait is needed, wait on a locator state, a network
  response (`page.waitForResponse`), or a URL change (`page.waitForURL`) — not a fixed delay.
- For toasts/snackbars that auto-dismiss, assert on the toast appearing and its text, not on it
  persisting; don't wait for it to disappear unless the test specifically checks that.

## Known risks and flaky patterns

- **Deep-link navigation can drop auth/session state (high risk, explicitly flagged for this
  analysis).** ToolBerry is a Quasar/Vue **offline-first SPA**. Navigating directly to a deep URL
  via `page.goto(url)` can force a full page reload that drops the app's in-memory session and
  spins up a fresh local workspace instead of resuming the authenticated one. **Prefer navigating
  via UI interactions** (clicking nav items, links, buttons) over `page.goto()` to a deep path once
  a test is already inside the authenticated app. Where a test must start from a specific record
  URL, establish auth state first (see "Auth" section) and verify the landing page actually reflects
  the signed-in workspace before proceeding, rather than assuming `goto()` preserved it.
  - Note on what was actually observed: the authenticated session's current URL
    (`https://qa.toolberry.app/w/<workspaceId>/transfer/<recordId>`) is **path-based**, not a `#`
    hash fragment. Whether that specific path style is what triggers the full-reload/session-drop
    behavior, or whether it's a separate SPA-router nuance, is **unconfirmed by this analysis** —
    treat the underlying risk (direct `goto()` to a deep path dropping session) as real either way,
    per the explicit note from the manual Transfer test run, but flag the exact mechanism as needing
    confirmation.
- **Workspace-scoped URLs.** Record URLs are scoped to a workspace id (`/w/<workspaceId>/...`).
  Hardcoding a workspace id in a spec ties that test to one specific QA workspace/dataset; prefer
  navigating from a list/search view and asserting on the resulting record rather than hardcoding
  ids where avoidable.
- **No `data-testid` coverage** means locator stability depends entirely on accessible names not
  changing. A copy change to a button or dialog title (e.g. renaming "Save & Open") will break every
  locator depending on that exact name — flag this as a maintenance cost when reviewing failures,
  not necessarily an app bug.
- **No password/API auth shortcut observed** (see "Auth") — this is the single biggest blocker to
  fully unattended automation and should be resolved before a CI pipeline (vs. an on-demand local
  run) is built around this suite.
- Standard SPA risks not yet specifically observed but worth assuming given the stack (Quasar/Vue,
  offline-first, local SQLite/OPFS per the main repo's architecture docs): modal/dialog open and
  animation transitions (wait on the dialog's role+name becoming visible, not a timeout); initial
  data sync/hydration on first load after sign-in (wait on a concrete element, e.g. the main nav or
  a specific list row, before interacting); third-party widgets were not encountered in the Transfer
  page snapshot analyzed.
- `trace: 'retain-on-failure'` and `screenshot: 'only-on-failure'` are already configured — use the
  HTML report (`data/outputs/4-automation/.report`) and traces to debug failures rather than adding
  ad hoc logging.
